<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| music module → Core `POST /modules/register` | machine-to-machine registration handshake authenticated by the forwarded `X-Sentinel-Key` header |
| deploy secrets → music container | the registration key is provided as a Docker secret file (`secrets/sentinel_api_key`), not a plaintext compose value |
| music module → Obsidian Local REST API | the module's own `ObsidianClient` carries `Authorization: Bearer {OBSIDIAN_API_KEY}` |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-48-05 | Spoofing | Unauthenticated module registration at POST /modules/register | medium | mitigate | The registration + heartbeat post `X-Sentinel-Key` (from the Docker secret / env), which Core already validates — unchanged Core behavior; no new registration mechanism is introduced (reuses the one seam). |
| T-48-06 | Information Disclosure | Registration key committed as a plaintext compose `environment:` value | high | mitigate | compose.yml references the key via a Docker `secrets:` block (`file: ../../secrets/sentinel_api_key`) and `env_file: ../../.env`; no secret is inlined in `environment:` (mirrors pf2e's documented pattern). |
| T-48-07 | Tampering (boundary breach) | Music accidentally importing Core's Vault Protocol couples the module to Core internals (MUS-02 violation) | medium | mitigate | `app/obsidian.py` composes only `ObsidianClientCore` from `sentinel_shared`; the MUS-02 import-boundary grep (Task 2 acceptance) must be empty. |
| T-48-SC | Tampering | package-manager installs | low | accept | Only already-pinned libraries (fastapi/uvicorn/httpx/pydantic-settings/pyyaml/pytest) are installed into the new venv; no new package name introduced (RESEARCH Package Legitimacy Audit — N/A). |
</threat_model>
