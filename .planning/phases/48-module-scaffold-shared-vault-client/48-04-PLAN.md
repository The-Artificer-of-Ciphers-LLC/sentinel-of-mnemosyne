<objective>
Land the module's first `music/` vault write and its compliance proof (MUS-02, MUS-05), and — in the SAME commit (D-13, Pitfall 1) — the generated sweeper protection that stops the vault sweeper from relocating those brand-new notes. The write is a 4-note cross-linked hub-mesh (D-08); compliance is proven structurally in-module against the vendored orphan rule (D-10), since Core's `:graph`/`:check` is hard-scoped to `NOTES_ROOT="notes"` and cannot see `music/`.

Purpose: Establish durable, zero-orphan link targets so Phase 49+ practice/idea/lesson notes resolve immediately, and guarantee those notes survive the next sweep — with zero Core app-code changes.
Output: `app/seed.py` (hub-mesh + writer), the module-side zero-orphan test, the env-override generator, the Core-side drift guard, and documented `.env.example` vars.

Namespace (D-07): `music/` is a new module-owned TOP-LEVEL vault namespace (sibling to `self/`, `notes/`, `ops/`) — not PARA-classified — with subfolders `music/lessons/`, `music/practice-log/`, `music/ideas/`. Deferred (D-15): warm-tier recall exclusion for `music/` is intentionally NOT wired here (it needs a Core `RecallConfig.exclude_prefixes` change with no env path, which MUS-01 forbids); accept that music notes may surface in generic warm-tier recall until a later phase wires exclusion alongside the deterministic `:music history` feature.

IMPORTANT — corrected hub-mesh design: Core's `resolve_wikilink` (sentinel-core/app/services/graph_analysis.py:56-72) matches wikilink targets strictly by UNIQUE filename stem. The RESEARCH Pattern 4 bodies name every note `index.md` (colliding stems) and link by full path (`[[music/lessons/index]]`), which does NOT resolve under that rule and would flag all four as orphans. This plan uses UNIQUE stems and BARE-stem wikilink targets instead (below) so the mesh is genuinely zero-orphan; the test is the gate that proves it.
</objective>

<commit_discipline>
## D-13 Atomicity — Seed Writer + Sweeper Protection Land in ONE Commit

Pitfall 1 / D-13 require that `music/`'s sweeper protection ship in the SAME commit as the code that performs the first `music/` write, so a first-write can never reach `main` (or a deploy build) without its protection. This plan is therefore the single, deliberate exception to GSD's one-commit-per-task rule:

- **Task 1 does NOT commit on its own.** After Task 1's verify is green, leave its files staged/uncommitted and proceed to Task 2. Do NOT create any intermediate commit between the two tasks.
- **Task 2 makes ONE atomic commit** covering BOTH tasks: `modules/music/app/seed.py`, `modules/music/app/main.py` (lifespan seed wiring), `modules/music/tests/test_music_vault_seed.py`, `modules/music/scripts/gen_sweep_protection_env.py`, `sentinel-core/tests/test_env_override_matches_core_defaults.py`, and `.env.example` — all in the same commit.
- **Verify the co-commit:** `git show --stat HEAD` (equivalently `git log --oneline --name-only -1 HEAD`) MUST list both `modules/music/app/seed.py` (the writer) and `modules/music/scripts/gen_sweep_protection_env.py` (the protection) in that single commit, and there must be no earlier commit that introduced `app/seed.py` without `gen_sweep_protection_env.py`. This is the verifiable acceptance of D-13's "same commit as the first write."
</commit_discipline>
