<objective>
Build the two note-quality six_rs stages as independent structured completions (D-05, Pattern 1): **Reduce** (`reduce.py`) extracts a durable-knowledge claim from one raw inbox entry into `{claim_title, body, schema_type}` with `response_format=json_schema`, and **Verify** (`verify.py`) reuses the already-shipped `note_schema.check_note_compliance` (D-02a) to decide pass/fail, adding only an optional claim-title natural-language assist on top. Reduce embodies Pitfall 6: it NEVER blocks or drops on imperfect LLM output — a malformed completion still yields a draft-fileable result. Reduce also owns the **net-new** `build_schema_block()` helper that constructs the trailing `_schema` fence the Wave-3 orchestrator appends to each note: Phase 45 was inspect-only (45-CONTEXT D-02) and shipped only PARSERS (`parse_schema_block`/`check_note_compliance`) — nothing in the tree CONSTRUCTS a block, so this builder is net-new here and is the literal `_schema`-writing mechanism behind PIPE-02/PIPE-03 and ROADMAP Success Criteria 2/3. Verify owns the named `VERIFY_RETRY_CAP` constant (D-02b) that the Wave-3 orchestrator uses to bound the requeue loop.

Purpose: The Reduce+Verify half of the 6 Rs — the write-a-note and enforce-quality-at-verify stages (PIPE-02 note authoring, PIPE-07 enforcement-at-Verify).
Output: `six_rs/reduce.py` + `six_rs/verify.py`, both pure transforms with graceful failure, turning their Wave-0 RED tests GREEN.
</objective>

| raw inbox entry text → Reduce LLM prompt | Untrusted captured content crosses into an LLM completion — a captured note could embed instructions to manipulate the model. |
| LLM completion output → ReduceResult → (Wave-3) vault write | Model output becomes note content; must be schema-validated before any write. |
